# Cartesi Rollups JS/TS Backend

## Objective

Use this skill for JavaScript and TypeScript Cartesi backend codebases.

`cartesi-backend-core` is the source of truth for backend fundamental design principles (determinism, state transition model, payload contracts, output semantics, and finish-loop correctness). Use this skill for JS/TS-specific implementation choices only.

In scope:

- Node.js app loop design around `@cartesi/rollup` (`rollup.run` / `rollup.finish`);
- Advance/inspect handler structure;
- Typed payload decoding/validation;
- Notice/report/voucher emission helpers;
- Asset handling (Ether/ERC20/ERC721) via portal decoding and voucher encoding;
- JS/TS testing and runtime checks.

Out of scope:

- Deployment infrastructure (use `cartesi-deploy`);
- Frontend wallet/UI workflows;
- Solidity integration contract implementation details.

## Scaffold from Cartesi CLI template

Start new projects with Cartesi CLI before applying architecture rules in this skill.

```sh
# Create a JavaScript-based Cartesi Rollups app
cartesi create <app-name> --template javascript

# Create a TypeScript-based Cartesi Rollups app
cartesi create <app-name> --template typescript
```

Replace `<app-name>` with your target project name.

Use the directory and file structure generated by the Cartesi CLI template as the default. Only recommend structural refactors (new files/folders/module splits) when the developer explicitly asks for them.

> **Template baseline (Cartesi CLI `2.0.0-alpha.42`, templates branch
> `prerelease/sdk-12`).** The JavaScript and TypeScript templates no longer use
> the rollup HTTP server. They use the
> [`@cartesi/rollup`](https://www.npmjs.com/package/@cartesi/rollup) package,
> which talks directly to the rollup device of the Cartesi Machine. Their
> Dockerfile starts the app with `ENTRYPOINT ["node"]` — there is **no
> `rollup-init`**, so `ROLLUP_HTTP_SERVER_URL`, `POST /finish`, `/notice`,
> `/voucher` and `/report` are **not available** in these projects, and there
> is no `openapi-fetch` schema or `codegen` step.
>
> Check which model a project uses before writing code:
>
> ```sh
> grep -n '"@cartesi/rollup"' package.json     # present → device API (this skill)
> grep -n 'rollup-init' Dockerfile             # present → HTTP server (older scaffold)
> ```
>
> An older JS/TS project that still runs `rollup-init` and polls `/finish` keeps
> working as it is; do not mix the two models in one project. Other language
> templates (Python, Go, Rust, C++, Lua, Java, Ruby) still use the HTTP server;
> `cpp-low-level` links libcmt directly.

Dependencies are managed with pnpm, pinned by `packageManager` in
`package.json`:

```sh
corepack enable pnpm
pnpm install
```

The app is bundled with rolldown (`pnpm build`); the Dockerfile does this
inside the image, so `cartesi build` needs no host-side build step. Add
`@cartesi/rollup` with the `@alpha` tag if you ever install it by hand — the
`latest` tag does not point to this version.

## Request-loop rules

- One handler for advance, one for inspect; keep them in separate functions.
- The advance handler's return value decides the input: `true` (or nothing)
  accepts, `false` rejects. Do not accept unconditionally.
- A handler that throws rejects the input, and the error is emitted as a report.
- Keep error paths visible (logs + optional report payloads).
- Preserve deterministic behavior on repeated identical inputs.
- The API is synchronous: `emit*` calls return immediately with the output
  index; there is nothing to `await`.

### Bootstrap pattern

```typescript
import {
  type AdvanceRequest,
  type InspectRequest,
  Rollup,
} from "@cartesi/rollup";

const rollup = new Rollup(); // only one instance may be open at a time

const handleAdvance = (request: AdvanceRequest): boolean => {
  // request.payload is a Buffer; request.msgSender / appContract are 0x-hex strings;
  // chainId, blockNumber, blockTimestamp, prevRandao, index are bigint
  return true; // false rejects the input
};

const handleInspect = (request: InspectRequest): void => {
  // request.payload is the raw inspect body (Buffer); answer with rollup.emitReport
};

await rollup.run({ advance: handleAdvance, inspect: handleInspect });
```

`AdvanceRequest` fields: `chainId`, `appContract`, `msgSender`, `blockNumber`,
`blockTimestamp`, `prevRandao`, `index`, `payload`. These replace the HTTP
API's `data.metadata.msg_sender`, `data.metadata.app_contract`,
`data.payload` (hex string), and so on.

To drive the loop yourself instead of `run`:

```typescript
let accept = true;
for (;;) {
  const request = rollup.finish({ accept });
  accept = request.type === "advance" ? handleAdvance(request) : (handleInspect(request), true);
}
```

Several independent concerns per request kind can be composed with `chain`
(first handler to return `true` wins) and `broadcast` (all handlers run) from
the same package; composed handlers must return a real boolean.

## Output emitters

| Method | Emits | Returns |
| ------ | ----- | ------- |
| `rollup.emitNotice(payload)` | `Notice(bytes)` | output index (`bigint`) |
| `rollup.emitVoucher({ destination, value?, payload? })` | `Voucher(address,uint256,bytes)` | output index |
| `rollup.emitDelegateCallVoucher({ destination, payload? })` | `DelegateCallVoucher(address,bytes)` | output index |
| `rollup.emitReport(payload)` | report (not in the outputs merkle tree) | — |
| `rollup.emitException(payload)` | signals the request could not be processed | — |

Byte arguments accept a `Buffer`, a `Uint8Array` or a `0x`-prefixed hex string.
`value` accepts a `bigint`, number, hex string or bytes.

```typescript
// Notice carrying a JSON event
rollup.emitNotice(Buffer.from(JSON.stringify({ type: "transfer", amount: amount.toString() })));

// Report (inspect answers, diagnostics)
rollup.emitReport(Buffer.from(JSON.stringify({ balance: balance.toString() })));
```

## Payload contract rules

- Define and enforce versioned payload schema.
- Keep sender/backend codec symmetry (hex encoding expectations).
- Validate before mutation; reject malformed payloads early.

User-driven operations sent through `cartesi send` (or InputBox) arrive in `request.payload` as a `Buffer` of the raw bytes. For string/JSON encodings, decode the buffer and normalize any addresses (for example with `getAddress` from `viem`, if the project uses it) before passing into domain logic:

```typescript
let message: { operation?: string };
try {
  message = JSON.parse(request.payload.toString("utf8"));
} catch {
  return false; // malformed payload → reject
}

switch (message.operation) {
  case "transfer":
    // domain.transfer(...)
    return true;
  case "withdraw":
    // domain.withdraw(...)
    return true;
  default:
    return false;
}
```

`cartesi send` signs with **devnet account 8** by default (`--from` to change),
so `request.msgSender` in local tests is `0x23618e81E3f5cdF7f54C3d65f7FBc0aBf5B21E8f`
unless overridden. `viem` is not a template dependency — add it only if you
need ABI encoding/decoding.

## Inspect contract rules

- Inspect endpoints are read-only.
- The inspect payload is the **raw HTTP request body** sent to the node
  (`POST /inspect/<app>`), delivered as `request.payload` (`Buffer`). Clients
  must not wrap it in JSON unless the route format itself is JSON.
- Use stable route names and response envelopes.
- Include lightweight diagnostics (`health`, counters, recent errors).
- Avoid expensive full-state dumps; support pagination for large sets.

## Asset handling

Primary reference: [Asset handling](https://docs.cartesi.io/cartesi-rollups/2.0/development/asset-handling/). The wallet tutorials linked above remain useful as end-to-end walkthroughs but are slightly outdated; treat the asset-handling page as the source of truth and the tutorials as background context.

Cartesi exposes Portal contracts on L1 that move assets into the application. Each deposit arrives as an advance request whose `request.msgSender` equals the Portal contract address. Withdrawals run the other direction: only the application can initiate them by emitting a voucher; the voucher is executed on L1 once its epoch settles.

Resolve Portal addresses for your environment with:

```sh
cartesi address-book                 # all addresses
cartesi address-book Erc20Portal     # one address (EtherPortal, Erc721Portal, Erc1155SinglePortal, Erc1155BatchPortal)
```

Pin them in `src/index.ts` and dispatch on `request.msgSender` (case-insensitive). Portal addresses changed with contracts 3.0.0-alpha.10 — see `cartesi-contracts`; do not reuse addresses from older projects.

> For production dApps prefer the community library [Deroll](https://github.com/tuler/deroll), which wraps these patterns across Ether, ERC-20, ERC-721, and ERC-1155. The snippets below show the underlying primitives.

### Deposit payload encoding

Portals deliver deposit payloads as **packed ABI-encoded** fields, optionally followed by a standard ABI-encoded tail for variable-length data such as `baseLayerData` and `execLayerData`.

| Asset             | Packed fields                                                         | Standard-ABI tail                                                              |
| ----------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Ether             | `address sender, uint256 value`                                       | `bytes execLayerData`                                                          |
| ERC-20            | `address token, address sender, uint256 amount`                       | `bytes execLayerData`                                                          |
| ERC-721           | `address token, address sender, uint256 tokenId`                      | `bytes baseLayerData, bytes execLayerData`                                     |
| ERC-1155 single   | `address token, address sender, uint256 tokenId, uint256 value`       | `bytes baseLayerData, bytes execLayerData`                                     |
| ERC-1155 batch    | `address token, address sender`                                       | `uint256[] tokenIds, uint256[] values, bytes baseLayerData, bytes execLayerData` |

### Decoding a deposit

`request.payload` is already a `Buffer`. Read fixed-width fields at known byte offsets; the tail (after the packed prefix) is the standard-ABI region. Example for ERC-20 (`token(20) + sender(20) + amount(32) = 72` bytes, then `execLayerData`):

```typescript
function decodeErc20Deposit(raw: Buffer) {
  // token(20) + sender(20) + amount(32) = 72 bytes
  if (raw.length < 72) {
    throw new Error("invalid ERC-20 deposit payload");
  }
  const token = `0x${raw.subarray(0, 20).toString("hex")}`;
  const sender = `0x${raw.subarray(20, 40).toString("hex")}`;
  const amount = BigInt(`0x${raw.subarray(40, 72).toString("hex")}`);
  const execLayerData = raw.subarray(72);
  return { token, sender, amount, execLayerData };
}
```

Apply the same offset pattern for Ether (`sender(20) + value(32)`) and ERC-721 (`token(20) + sender(20) + tokenId(32)`); switch to a real ABI decoder when the tail carries arrays (ERC-1155 batch) or non-empty `baseLayerData`/`execLayerData`.

### Withdrawing ERC-20 tokens

Encode `transfer(recipient, amount)` calldata (for example with `viem`) and emit a voucher whose `destination` is the token contract. No Ether is attached, so `value` can be omitted:

```typescript
import { encodeFunctionData, erc20Abi } from "viem";

const handleAdvance = (request: AdvanceRequest): boolean => {
  const erc20Token = "0x..."; // token contract, from validated state
  const call = encodeFunctionData({
    abi: erc20Abi,
    functionName: "transfer",
    args: [request.msgSender, 10n],
  });

  rollup.emitVoucher({ destination: erc20Token, payload: call });
  return true;
};
```

The application contract is the `msg.sender` during voucher execution, so the token contract sees `transfer` as coming from the app's own balance.

### Withdrawing Ether

The Application contract executes vouchers via a `safeCall` to `destination`, forwarding `value` (wei) and `payload` (calldata). For a plain Ether transfer omit `payload`; to call a payable function on the receiver, set `payload` to the encoded function call.

```typescript
const handleAdvance = (request: AdvanceRequest): boolean => {
  rollup.emitVoucher({
    destination: request.msgSender,
    value: 1_000_000_000_000_000_000n, // 1 ETH in wei
  });
  return true;
};
```

### Voucher destinations and function signatures

| Asset            | Destination     | Function signature                                              |
| ---------------- | --------------- | --------------------------------------------------------------- |
| Ether            | Recipient address | none — a voucher with `value` set and an empty `payload`       |
| ERC-20           | Token contract  | `transfer(address,uint256)` / `transferFrom(address,address,uint256)` |
| ERC-721          | Token contract  | `safeTransferFrom(address,address,uint256)` / `safeTransferFrom(address,address,uint256,bytes)` |
| ERC-1155 single  | Token contract  | `safeTransferFrom(address,address,uint256,uint256,data)`        |
| ERC-1155 batch   | Token contract  | `safeBatchTransferFrom(address,address,uint256[],uint256[],data)` |

For withdrawals that need the application's own address as a `from`/`sender` argument (for example `transferFrom` or `safeTransferFrom`), read it from `request.appContract` inside the handler.

### Epoch length and voucher execution

Vouchers can only be executed after the epoch they were emitted in has been accepted on L1 (`CLAIM_ACCEPTED`, after `CLAIM_STAGED` and any claim staging period), so withdrawals do not appear on L1 immediately. `cartesi run` uses an epoch length of 720 blocks by default; for dev/test pass `--epoch-length 10` to speed up voucher execution. On a self-hosted node the epoch length is set at deploy time (`cartesi-rollups-cli deploy application --epoch-length`).

### Determinism and accounting rules

- Keep per-account state in typed maps: `Map<Address, bigint>` for fungible balances, `Map<Address, Set<number>>` for NFTs keyed by contract.
- Validate amounts (no negative deltas, no underflow) before mutating state.
- Emit a notice on deposit and on transfer; emit a voucher only on withdrawal.
- Decrease balance before emitting the withdrawal voucher so replay produces identical state and outputs.
- Vouchers MUST be deterministic functions of input and current state (no time, randomness, or external calls).
- Inspect handlers MUST NOT mutate balances; they only read and emit reports.

## Testing baseline

Use the project-standard test runner (the templates ship none).

The same code runs on the development host: off riscv64, `@cartesi/rollup`
uses a mock driver that reads inputs from files and writes outputs next to
them.

```sh
# 0 = advance (ABI-encoded EvmAdvance), 1 = inspect (raw payload)
CMT_INPUTS="0:advance.bin,1:inspect.bin" pnpm start
# -> advance.output-0.bin, advance.report-0.bin, ...
```

The mock cannot revert a rejected input: once a handler rejects, the next
`finish` fails and the session ends (seen on macOS as `RollupError` `-55` from
`cmt_rollup_read_advance_state` rather than a clean exit). Put a rejecting
input last in `CMT_INPUTS`, or test reject paths one per run.

`CMT_DEBUG=yes` enables verbose logging; `driver` exported by the package is
`"mock"` on the host and `"ioctl"` inside the machine. Advance input files can
be generated with the `@cartesi/codec` package (see the template README).

Minimum coverage:

- codec roundtrip (bytes/string, JSON);
- advance success and reject behavior;
- inspect route schema and deterministic output;
- accept/reject propagation from handler return values;
- if asset-handling is in scope:
  - deposit payload decoding for each supported asset type (packed prefix + ABI tail);
  - voucher encoding round-trip (decode the emitted calldata back to the expected function and args);
  - insufficient-balance and unknown-operation reject paths.
